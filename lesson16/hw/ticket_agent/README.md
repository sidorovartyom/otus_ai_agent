# Домашнее задание 16: логика выполнения агента

## Задача

Обработка заявки в техподдержку Otus Cloud: агент принимает обращение,
классифицирует его, в зависимости от категории обращается к нужному
инструменту, формирует ответ и сохраняет результат в память.

## Схема (граф состояний)

```
[1] receive_ticket
      │  (client_id, text) -> ticket + чтение истории клиента из памяти
      ▼
[2] classify_ticket (LLM, forced tool-use)
      │  category ∈ {billing, technical, other}
      ▼
[3] route_and_resolve  ───────── ВЕТВЛЕНИЕ ─────────
      │                    │                    │
   billing              technical              other
      │                    │                    │
 lookup_invoice()   search_knowledge_base()      │
   (мок API)             (файл KB)               │
      │                    │                    │
      ▼                    ▼                    │
  ПРОВЕРКА: счёт      ПРОВЕРКА: статья           │
  найден?              найдена?                  │
   да │ нет            да │ нет                  │
      │   └──────┐        │   └──────┐           │
      ▼          ▼        ▼          ▼           ▼
  (result)   ЭСКАЛАЦИЯ  (result)  ЭСКАЛАЦИЯ   ЭСКАЛАЦИЯ
      │          │        │          │           │
      └──────────┴────────┴──────────┴───────────┘
                          │
                          ▼
[4] compose_reply (LLM)
      │  формирует ответ клиенту с учётом tool_result / эскалации
      ▼
[5] log_to_memory
      │  запись {ticket, category, escalated, reply} в memory.jsonl
      ▼
    конец
```

## Компоненты

| Файл             | Роль                                                           |
|------------------|------------------------------------------------------------------|
| `pipeline.py`     | Оркестрация: 5 шагов, ветвление и проверка в `route_and_resolve` |
| `llm.py`          | Подключение к Anthropic API; `classify_ticket` (forced tool-use), `compose_reply` |
| `tools.py`        | Инструменты: `search_knowledge_base` (файл), `lookup_invoice` (мок биллингового API) |
| `memory.py`       | Файловая память истории обращений (`memory.jsonl`), `append_ticket` / `get_history` |
| `knowledge_base.md` | База знаний для инструмента `search_knowledge_base`             |
| `demo.py`         | Пример выполнения: 4 заявки, покрывающие обе ветки и эскалацию   |

## Почему классификация через forced tool-use

Шаг 2 форсирует вызов tool (`tool_choice={"type": "tool", "name": "classify_ticket"}`)
с `enum` в схеме (`billing`/`technical`/`other`). Это гарантирует валидную
категорию без парсинга свободного текста и без риска, что модель
ответит в неожиданном формате — управление логикой (шаг 3) полностью
детерминировано и не зависит от вариативности текста модели.

## Запуск

Из папки `lesson16/hw` (нужен `.env` в корне репозитория, как в lesson04/lesson09):

```bash
python -m ticket_agent.demo
```

`llm.py` сам определяет, какой пакет нужен для `http_client` (`httpx`
или `httpx2`), поэтому команда работает и с глобальным Python, и с venv.

Память (`memory.jsonl`) накапливается между запусками — при повторном
запуске demo.py для client_1 в шаге 1 будет видно больше найденных
предыдущих обращений. Чтобы начать сценарий "с чистого листа", удалите
`ticket_agent/memory.jsonl` перед запуском.
